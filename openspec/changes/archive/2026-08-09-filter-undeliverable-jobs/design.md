## Context

现状（见 proposal.md 的 Why）：搜索管道 `engine.run_search` 的硬指标过滤依赖列表卡片文本与意向文本正则，下线校验只覆盖 51job 且靠 HTTP 详情页，BOSS直聘/实习僧候选不做详情核实。`config/user_profile.json` 已含可靠画像（`resume_parse` 中的「学历:大专」与 `city` 字段），但搜索未读取。

约束：纯 stdlib（LLM 除外）、数据本地化、登录门禁、投递必验证；三平台详情页行为需在实现期用真实登录态实测。

## Goals / Non-Goals

**Goals:**

- 展示给用户的候选列表不再包含不可投递岗位：已下线/审核中、学历或地点硬性不达标、以及无法核实有效性的岗位。
- 硬指标过滤使用 `config/user_profile.json` 画像与岗位详情页数据，列表卡片文本仅兜底。
- 校验不可用时直接过滤，绝不展示或要求人工确认；最终无结果时如实告知。

**Non-Goals:**

- 不引入新的用户配置项或修改 `user_profile.json` / `applications.json` 格式。
- 不做搜索结果的实时刷新（投递阶段的下线拦截逻辑保持不变）。
- 不改变 LLM 评分 API 与 Dashboard API 契约。
- 经验年限不参与任何硬性过滤与评分否决（经验要求通常不满足，不应成为拦路项）。

## Decisions

### D1：画像来源统一为 `config/user_profile.json`，意向文本仅兜底

新增 `load_user_profile()`：读取 `config/user_profile.json`，从 `resume_parse` 提取最高学历（正则 `学历[:：]\s*(博士|硕士|本科|大专|中专|高中|研究生)`，研究生归一为硕士），目标城市取 `city` 字段。`_user_profile(intent)` 改为 `_user_profile(intent, resume_parse)`：先画像、后意向文本兜底；两者都缺失时该硬指标不启用并在警告中提示「画像缺少学历/城市，学历/地点硬过滤未完全生效」。

**备选**：让 Dashboard 保存时输出结构化字段。被否——改动保存逻辑与文件格式，超出本变更范围。

### D2：详情页核实统一入口 `verify_job(job) -> dict`

一次核实同时产出三项：

- `offline`: 详情页文本命中 `OFFLINE_MARKERS`（强特征词，如「已下线」「审核中」「职位不存在」）
- `degree`: 从详情文本提取的最低学历（复用 `_jd_required_degree` 的正则）
- `location`: 从详情文本提取的城市（统一走 D3 的 `extract_city`）
- `verified`: True=详情页成功读取；False=网络/风控/登录墙导致无法核实

按平台实现：

- 51job：HTTP 请求详情页（现有 `job_offline` 改造）；详情页为服务端渲染，可直接读正文。
- BOSS直聘 / 实习僧：Camofox 打开详情页，取 `document.body.innerText`（复用 browser 客户端；并发 tab 数 ≤ 3，校验完立即 close_tab）。登录墙出现时视为 `verified=False`。

### D3：地点判断改为「先提取城市名再比对」，杜绝截断漏判

新增 `extract_city(text)`：遍历 `CITY_CODES` 城市表，返回文本中出现的第一个城市名（排除「全国」「不限」等词）；同时修正实习僧卡片解析正则，`location` 取「城市-区/县」完整片段而非仅末尾区名。`_hard_filter` 逻辑改为：若 `extract_city(卡片 location)` 有值且 ≠ 目标城市 → 剔除；卡片只有区名/无城市 → 交给 D2 详情页核实；详情页城市 ≠ 目标城市 → 剔除。

### D4：先评分、取前 10、再详情核实（控制核实数量与耗时）

列表卡片数据不可信（BOSS 列表的地点/学历标注可能与详情不符，见 `references/boss-pitfalls.md`），但每轮搜索**最多只对 10 个岗位开详情页**，顺序为：

1. 卡片级确定性硬过滤：51job API 的学历/地点可信，评分前剔除；BOSS/实习僧卡片数据仅作参考。
2. LLM 评分 → 3 星及以上按分数降序取前 10 名。
3. 仅对这 ≤10 个岗位开详情页核实（下线/学历/地点一次拿全），核实通过且硬指标满足才展示。

目的：既保证展示的岗位经过详情页验证（杜绝「卡片南京、详情长沙」与「已下线」泄漏），又把浏览器核实控制在 10 个以内，避免单轮搜索耗时过长。浏览器并发 tab ≤ 3（platforms 信号量），51job 走廉价 HTTP 详情；进度反馈显示 `(已核实/10)`。

### D5：校验失败与不合格岗位——直接过滤，绝不展示

`verify_job` 返回 `verified=False`（无法核实）或核实不通过（下线/学历或地点不达标）时：岗位直接过滤，不进入结果列表、不要求用户人工确认。最终结果为空时如实返回 0 个岗位并提示「未找到合适的岗位」，不放宽硬指标或评分门槛用不合适的岗位凑数；仅汇总计数（`filtered`/`offline`）供用户了解过滤量，不展示具体被过滤岗位。

## Risks / Trade-offs

- **详情页频繁访问触发风控/IP 黑名单** → 并发 tab 数 ≤ 3、每岗位超时 10s、失败不重试；仍失败时按 D5 直接过滤。
- **搜索总时长增加**（多岗位开详情页） → 阶段 1 只在卡片数据不足时核实；进度反馈分步展示，避免「无响应」观感。
- **详情文本误匹配失效词**（如正文引用「已下线」示例） → 仅匹配强特征词（现状 `OFFLINE_MARKERS` 已是最小集），并在实现期实测校准。
- **51job HTTP 详情被 WAF 拦截** → 拦截/异常视为 `verified=False`，按 D5 直接过滤。
- **BOSS 详情页登录墙** → 复用登录检测；未登录时该平台候选标 `verified=False` 直接过滤，不自动登录（登录门禁铁律）。

## Migration Plan
